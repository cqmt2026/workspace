## 二、模块化

### 定义
模块间低耦合、高内聚，每个模块可独立开发、独立测试、独立替换。

### 逐项确认

| 要求 | 现状 | 判定 |
|------|------|------|
| 层间单向依赖 | 严格执行：Dashboard→Execute→Backtest→Portfolio→Strategy→Feature→DataHub | ✅ |
| 禁止跨层调用 | 明确列出禁止项（Strategy→DataHub、Backtest→Feature等） | ✅ |
| 模块可独立开发 | 每个模块有独立的目录和文件 | ✅ |
| 模块可独立测试 | tests/ 目录包含每个模块的测试文件 | ✅ |
| 模块可独立替换 | 适配器模式（数据源可替换）、策略基类（策略可新增） | ✅ |
| 新增功能不修改旧模块 | 模块修改规则已明确 | ✅ |
| 修复bug不跨层 | 同一层内修复，不改其他层 | ✅ |

**模块化判定：✅ 达标**

确认方法：架构图中每个模块的输入输出接口明确，层间依赖规则已书面化，新增功能只需新增文件不修改旧文件。

## 三、标准化

### 定义
模块间通过标准数据格式通信，接口统一，配置统一，日志统一。

### 逐项确认

| 要求 | 现状 | 判定 |
|------|------|------|
| 数据标准统一 | Signal/Order/Account/Context/Result 全部定义为 dataclass | ✅ |
| K线格式统一 | KLINE_COLUMNS 明确定义 | ✅ |
| 因子格式统一 | FACTOR_COLUMNS 明确定义 | ✅ |
| 接口标准统一 | 适配器接口标准（connect/disconnect/get_bars/health_check） | ✅ |
| 配置统一管理 | 所有模块通过 ConfigManager 读取配置，不硬编码 | ✅ |
| 日志统一管理 | 所有模块通过 Logger 写日志 | ✅ |
| 置信度输出标准化 | ML策略=预测概率，规则策略=条件满足度映射到0~1 | ✅ |
| 配置文件模板化 | data.yaml/features.yaml/models.yaml/strategies//backtest.yaml/risk.yaml | ✅ |
| 错误处理标准化 | 自定义异常类，统一异常处理 | ✅ |

**标准化判定：✅ 达标**

确认方法：所有数据格式用 dataclass 定义，所有配置通过 ConfigManager，所有日志通过 Logger，模块间通信不走内部方法。

## 四、可能存在的问题

### 4.1 现有的 scripts/ 和 experimental/ 目录怎么办

**问题**：现有约50个脚本（strategy_scan.py、multi_factor_scoring.py、rps_push.py 等）和新框架不兼容。

**处理方案**：
- 新框架搭建期间，现有脚本继续运行（不中断现有Cron任务）
- 新框架的 DataHub 提供接口，现有脚本可以逐步迁移调用新框架的数据
- 新框架的策略跑通后，逐一替换现有脚本
- 现有脚本保留为"策略原型库"，不删除

### 4.2 学习成本

**问题**：新框架约80个文件，用户需要学习才能上手。

**处理方案**：
- 提供 examples/ 目录（run_backtest.py / create_strategy.py / run_optimization.py）
- 提供 docs/QUICKSTART.md
- 策略基类 BaseStrategy 的接口尽量简单（on_start / on_bar / on_end）

### 4.3 测试覆盖

**问题**：新框架的测试覆盖率需要保证。

**处理方案**：
- 每个 Phase 完成后必须通过单元测试才能进入下个 Phase
- 集成测试在 Phase 9 统一执行
- 关键路径（回测引擎）需要更高的测试覆盖率
