## 一、现状诊断

### 当前因子碎片分布

| 体系 | 所在位置 | 因子数 | 类别 | 与框架关系 |
|------|---------|--------|------|-----------|
| FeatureEngine 预置 | `alice_quant.features.calculators.technical` | 10 | 技术 | 已注册，纯价量 |
| 多因子评分 | `scripts/multi_factor_scoring.py` | ~30+ | 技术/资金/融资/风控/舆情/ML | 独立，与框架无关联 |
| PPE因子 | `scripts/ppe_factor.py` | 2 | 板块周期 | 独立，依赖RPS历史文件 |
| SmartMoney | `scripts/smart_money_factor.py` | 4 | 资金流 | 独立，依赖HTTP API |
| 形态捕手 | `scripts/xingtai_integration.py` | 6 | 形态识别 | 独立，依赖DB K线 |

**核心问题**：
1. 同一股票的评分逻辑分散在5个互不调用的脚本中
2. 因子计算不可复用 — pipeline策略只能用10个预置因子
3. 无因子IC监控 — 不知道哪些因子真有用
4. 因子值不持久化 — 回测每次都要重新算

### 目标架构

```
FeatureEngine (单一入口)
├── calculators/technical.py    ← 已有（扩容）
├── calculators/fundamental.py  ← 新建（基本面）
├── calculators/money_flow.py   ← 新建（资金流）
├── calculators/sentiment.py    ← 新建（舆情/ML）
├── calculators/pattern.py      ← 新建（形态）
└── calculators/sector.py       ← 新建（板块）

FactorRegistry (统一注册)
    ↓
FactorStore (SQLite持久化)
    ↓
IC Monitor (自动计算+淘汰)
    ↓
Pipeline Strategy (统一调用)
```

### Phase 2 — IC监控落地（1天）

#### 2.1 现有IC计算流程补齐

`FeatureEngine.compute_ic()` 已有架子但从未运行过，需要：

1. 回测时自动计算每日因子IC
2. 写入 `ic_history` 表到 factors.db
3. 每日收盘后计算全市场因子IC（独立脚本）

#### 2.2 因子淘汰机制

```python
# 自动淘汰条件（任一满足）
- IC均值 < 0.01 (60日滚动)
- IC正率 < 45%
- 覆盖度 < 60% (可计算股票数/全市场)
```

#### 2.3 IC报告输出

```python
# 输出格式
{
  "date": "2026-07-05",
  "factors": [
    {"name": "ma_5", "mean_ic": 0.035, "ic_ir": 0.42, "positive_ratio": 0.58, "status": "active"},
    {"name": "rsi_14", "mean_ic": 0.012, "ic_ir": 0.18, "positive_ratio": 0.52, "status": "watch"},
    {"name": "flow_intensity", "mean_ic": -0.008, "ic_ir": -0.15, "positive_ratio": 0.43, "status": "eliminated"}
  ]
}
```

### Phase 3 — 因子持久化（1天）

#### 3.1 现有 FactorStore 验证

FactorStore 已实现 SQLite 持久化 + 内存LRU缓存，但从未在生产中启用。需要：

1. 确认 `_get_db_path()` 指向正确的DB路径
2. 新增每日因子计算脚本 `scripts/daily_factor_compute.py`
3. 注册为 Cron 任务（16:45执行）

#### 3.2 每日因子计算流程

```
16:35 K线入库完成
    ↓
16:45 daily_factor_compute.py 启动
    ↓
从DB读取全市场当日K线
    ↓
FeatureEngine.precompute_all(codes, [today])
    ↓
FactorStore.save_factors_batch(缓存数据)
    ↓
IC计算
    ↓
报告输出到 out_data/factor_ic_{date}.json
```

### Phase 4 — 策略升级 ✅ 完成

#### 4.1 Pipeline v2 策略

`alice_quant.strategies.pipeline` 已升级为6维度综合评分系统：

| 维度 | 权重 | 因子来源 |
|------|------|---------|
| 动量趋势 | 30% | ma排列 + sector_phase + relative_strength |
| 量能确认 | 20% | vol_ratio + flow_intensity + flow_persistence |
| 价格形态 | 15% | pattern_strength/reversal/wbottom + price_confirmation |
| 基本面 | 15% | pe_ttm + pb + market_cap |
| 情绪信号 | 10% | mx_sentiment + ml_prob_lgb |
| 安全性 | 10% | 涨幅过滤 + RSI过滤 + 排除ST/北交所 |

#### 4.2 核心变化

- 买入信号从4个条件升级为6维度评分（0~100分）
- 评分 >= 50 分才纳入候选
- 卖出逻辑增强：跌破MA20 / 评分偏低 / M头预警
- 市场状态分三级：bull(正常)/bear(减仓)/stop(清仓)
- 大盘5日涨幅 < -5% 时自动清仓

#### 4.3 与现有脚本的衔接

- `scripts/multi_factor_scoring.py` 保持不变（独立评分参考）
- `scripts/strategy_scan.py` 保持不变（独立选股工具）
- Pipeline v2 作为AliceQuant框架的标准策略
- 因子数据优先从 factors.db 读取，FeatureEngine实时计算为降级

## 三、风险与注意事项

### 已知风险

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| SmartMoney依赖HTTP API | 稳定性不如DB | 保留回退到DB K线计算简化版 |
| 基本面因子需要外部API | 可能被限流 | 缓存+增量更新 |
| 板块RPS依赖收盘后生成 | 盘中因子不可用 | 因子标记update_frequency=end_of_day |
| 35个因子全量计算耗时 | 回测性能 | precompute_all机制已设计好 |

### 不迁移的部分

- `scripts/multi_factor_scoring.py` — 已经成熟稳定，作为独立评分参考
- `scripts/smart_money_factor.py` — 保留作为独立诊断工具
- `scripts/ppe_factor.py` — 保留，因子值通过 `factor_registry` 引用而非迁移代码
