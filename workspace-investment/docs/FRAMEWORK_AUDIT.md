# AliceQuant 框架深度评估报告

> 目标：从"功能完整"到"逻辑闭环"
> 逐层评估每个模块的真实作用、流程合理性、缺失项
> 时间：2026-07-05

---

## 评估方法

不走一遍完整逻辑流，是发现不了问题的。所以我从"系统最终要输出什么"倒推：

**系统最终输出**：每日交易信号（买入/卖出/持有），以及交易后的绩效报告。

要得到这个输出，需要经过的完整路径：

```
原始数据 → 清洗校验 → 因子计算 → 因子筛选 → 策略计算 → 信号生成
  → 风控检查 → 订单生成 → 成交记录 → 绩效统计 → 报告输出
```

在这个路径上，每个环节都要问：**"这个模块是否在为最终输出服务？是否有冗余？是否有遗漏？"**

## 1. 配置管理层 ConfigManager

### 功能作用
所有模块读取配置的统一入口。

### 评估
✅ 设计合理。多级覆盖（默认→用户→环境变量→命令行）是标准做法。
✅ 配置验证是必要的。
⚠️ 但缺少 **配置变更监听机制**。如果运行时改了某个策略参数，需要重启才能生效。对于需要频繁调参的场景（如回测优化），这是痛点。

### 结论
✅ 通过。建议加一个 `watch(key, callback)` 机制做运行时热更新。

---

## 2. 日志管理层 Logger

### 功能作用
所有操作可追溯。

### 评估
✅ 设计合理。
⚠️ 但缺少 **结构化日志**。当前的日志都是文本，查询和分析不方便。专业做法是用JSON格式记录关键事件，方便后续分析。

### 结论
✅ 通过。建议加结构化日志（JSON格式，关键字段可查询）。

## 3. 数据层 DataHub

### 功能作用
系统的基础设施。所有上层模块依赖的数据都从这里来。**数据质量直接决定策略质量的下限。**

### 评估

#### ✅ 好的部分
- 元数据管理（股票/日历/事件）是必要的
- 复权管理（前/后复权+复权因子）是必要的
- 数据质量管理（校验/评分/修复）是核心
- 多级缓存设计合理
- 适配器模式支持多数据源

#### ❌ 发现的问题

**问题1：缺少数据版本管理。**
回测时用的数据和实盘时用的数据必须是同一份。如果回测时用了2026-07-04的数据，但后来发现那天数据有误修复了，回测结果就变了。**没有数据版本管理，回测结果不可复现。**

**问题2：缺少快照机制。**
回测需要"在T日只能看到T日及之前的数据"。DataHub应该支持"时间旅行"——给定一个日期，返回该日期时的数据快照。现在没有这个机制，回测中策略可能"看到"未来数据。

**问题3：财务数据缺失。**
财务数据是基本面因子和模型训练的基础。现在API里有 `get_fundamentals` 但没说数据源。akshare和efinance的财务数据是否完整？缺失率多少？这些需要评估。

### 结论
⚠️ **有3个问题需要修复：数据版本管理、时间旅行快照、财务数据源评估。** 不改的话回测不可复现、可能存在前瞻偏误。

## 4. 特征工程层 Feature

### 功能作用
将原始数据转化为有预测力的特征。**这是策略收益的核心来源。**

### 评估

#### ✅ 好的部分
- 因子注册中心设计合理
- 因子分类完整（价量/资金/基本面/情绪/宏观/ML）
- 自动特征生成（时序/交叉/排序/非线性）是必要的
- 因子筛选（IC/分组/相关性/衰减/拥挤度）是核心
- 因子淘汰机制是必要的

#### ❌ 发现的问题

**问题1：因子计算引擎的增量更新和全量计算的关系没说清楚。**
一个因子第一次算需要全量历史数据，之后只需要增量。但如果因子计算逻辑变了（比如MA窗口从5改成10），增量就无效了，需要重新全量计算。**现在缺少因子版本管理**，没法判断因子是否需要重新计算。

**问题2：因子存储的中性化顺序有问题。**
现在写的顺序是"去极值→标准化→中性化"。但正确的顺序是"去极值→中性化→标准化"——先中性化去除市值/行业影响，再标准化到统一量纲。顺序错了因子值会偏差。

**问题3：缺少因子IC的滚动监控图。**
因子筛选里有IC分析，但只是静态的。专业的做法是每天计算当日IC，画成滚动曲线，一眼能看到因子是否在退化。现在缺少这个机制。

### 结论
⚠️ **3个问题：因子版本管理、中性化顺序、滚动IC监控。** 都是细节，但影响很大。

---

## 5. 模型训练层 ModelTrain

### 功能作用
用历史数据训练ML模型，输出ML因子给特征层。

### 评估

#### ✅ 好的部分
- 模型定位清晰（因子生成器，不是决策者）
- 训练原则正确（滚动训练、用因子做特征、定期重训）
- 样本管理/特征管理/模型管理设计完整

#### ❌ 发现的问题

**问题1：模型训练和回测的耦合没说清楚。**
文档里写了"Step 1-5"的滚动训练+回测流程，但这在实际实现中有个问题：回测引擎每推进一天都要重新训练模型，训练耗时会导致回测极慢。**需要明确：回测中的模型训练是实时训练还是预计算？**

如果是预计算（先算好每天的ML因子，再跑回测），那就意味着模型训练要跑在回测引擎之外。现在的架构图里没有体现这个关系。

**问题2：缺少模型训练的调度机制。**
现在写了"每月重训"，但没说明谁触发这个重训。是Cron任务？是回测引擎？还是手动？需要明确调度关系。

**问题3：多模型融合策略缺失。**
模型评估里有"模型融合效果"的对比，但没说融合的具体方法。最简单的融合是加权平均，更高级的是Stacking。需要明确融合策略。

### 结论
⚠️ **3个问题：训练与回测的时序关系、训练调度机制、融合策略。** 如果不解决，模型训练层和回测层无法正常协作。

## 6. 策略层 Strategy

### 功能作用
根据因子生成买卖信号。

### 评估

#### ✅ 好的部分
- BaseStrategy 基类设计合理
- 信号格式标准
- 预置策略库覆盖了主流策略类型

#### ❌ 发现的问题

**问题1：缺少策略缓存机制。**
策略在回测中每天都要调 `feature.get_factor()`。如果因子计算很慢（比如全市场排名），每次调用都重新计算会非常慢。**策略层应该有自己的因子缓存**——在 `on_start` 时预加载所有需要的因子，`on_bar` 时只从缓存读取。

**问题2：策略信号没有置信度校准。**
Signal 有 `confidence` 字段，但没说这个值怎么来。不同策略的置信度含义不同（ML策略的0.6和规则策略的0.6不是一回事）。**需要标准化置信度输出**，否则组合管理在融合信号时无法比较。

### 结论
⚠️ **2个问题：因子缓存机制、置信度标准化。** 影响回测速度和信号融合质量。

---

## 7. 组合管理 Portfolio Manager

### 功能作用
多策略信号融合、资金分配、风险预算。

### 评估

#### ✅ 好的部分
- 信号融合方法多样（等权/IC/夏普/动态/贝叶斯）
- 资金管理模型完整（凯利/固定比例/风险平价）
- 风险预算设计合理

#### ❌ 发现的问题

**问题1：缺少策略相关性管理。**
如果两个策略高度相关（比如趋势跟踪和均线突破），它们同时发出的信号不能简单加权——实际上相当于同一个信号被重复计数。**需要在融合前计算策略相关性，对高相关策略降权。**

**问题2：缺少再平衡触发条件。**
写了 `rebalance(target_weights)` 但没说什么时候触发。是固定周期（每周/每月）？还是偏离阈值（某股票权重偏离目标10%）？还是组合波动率变化？需要明确。

### 结论
⚠️ **2个问题：策略相关性管理、再平衡触发条件。** 都是组合管理中容易忽略但影响大的问题。

---

## 8. 回测层 Backtest

### 功能作用
验证策略有效性，严格控制前瞻偏误和过拟合。

### 评估

#### ✅ 好的部分
- 事件循环生命周期完整
- 订单管理/账户管理/绩效分析设计专业
- 过拟合检测方法全面（交叉验证/夏普衰减/参数敏感/随机检验/多重比较）

#### ❌ 发现的问题

**问题1：缺少回测结果对比功能。**
现在只有一个 `compare(results)` API，但没说比较什么。**专业的回测框架应该有回测结果数据库**，可以对比不同策略、不同参数、不同时间段的表现，用统一的指标排序。现在没有这个机制，做一次参数优化要人工对比结果。

**问题2：缺少回测数据范围校验。**
回测时策略可能请求了不存在的数据（比如某股票2020年还没上市）。**回测引擎需要在初始化时校验数据范围**，对数据不足的股票给出警告或自动剔除。

**问题3：回测和实盘的账户模型不一致。**
模拟交易用的是 `PaperTrading`，回测用的是 `AccountManager`。虽然功能相似，但代码不统一。**专业做法是回测和模拟交易共用同一套账户模型**，确保回测结果能真实反映到模拟交易。

### 结论
⚠️ **3个问题：回测结果对比/数据库、数据范围校验、账户模型统一。** 影响回测效率和结果可信度。

---

## 9. 执行层 Execution

### 功能作用
信号转订单、模拟/实盘交易、风控。

### 评估

#### ✅ 好的部分
- 信号处理器设计完整
- 风控模块细致（交易前/中/后/持仓）
- 模拟交易逻辑完整

#### ❌ 发现的问题

**问题1：风控规则和策略层的边界模糊。**
策略层有 `on_bar` 可以生成信号，风控模块也有止损逻辑。如果策略生成了一个买入信号，但风控模块因为"大盘暴跌"拒绝了，这个拒绝信息需要反馈给策略吗？**现在缺少风控结果回传机制。**

**问题2：缺少紧急停止机制。**
如果系统发现严重问题（数据异常/模型崩溃/风控反复触发），需要能一键停止所有交易。现在没有这个机制。

### 结论
⚠️ **2个问题：风控结果回传、紧急停止机制。** 影响系统安全性。

## 10. 监控层 Dashboard

### 功能作用
绩效可视化、风险监控、告警推送。

### 评估

#### ✅ 好的部分
- 绩效面板完整（净值/回撤/月度/持仓/归因）
- 风险面板完整（VaR/回撤/波动率/集中度）
- 告警系统完整（规则/级别/推送/处置）
- 系统监控完整（任务/数据/性能/健康检查）

#### ❌ 发现的问题

**问题1：缺少自动化报告。**
现在是"需要什么看什么"，但专业的做法是**每日自动生成一份标准报告**，包含当天交易、持仓、绩效、风险状态。不需要人工去查。

**问题2：告警阈值写死在设计里。**
回撤告警写的是5%/10%/15%，但不同策略的容忍度不同。**告警阈值应该通过 ConfigManager 配置**，不是硬编码。

### 结论
⚠️ **2个问题：自动化报告、告警阈值可配置。** 不影响核心功能，但影响使用体验。

## 11. 流程合理性评估

### 当前数据流

```
DataHub → Feature → Strategy → Portfolio → Backtest → Execute → Dashboard
                      ↑
                ModelTrain
```

### 发现的问题

**问题1：ModelTrain 和 Backtest 的时序冲突。**
ModelTrain 需要先训练才能输出ML因子，但 Backtest 在回测中需要每天用到ML因子。如果回测跨度5年（2019-2024），难道每天都要重新训练一次模型？

**解决方案：** 回测中的模型推理应该是**预计算**的。

```
正确流程:
  1. 先离线训练模型，输出历史每天的ML因子 (预计算)
  2. 将ML因子存入 Feature 层
  3. 回测引擎直接读取预计算的ML因子 (不需要在回测中训练)

  这样回测速度快，且训练和回测解耦。
```

**问题2：Feature 层既要给 Strategy 提供因子，又要给 ModelTrain 提供训练特征。但两者的数据范围不同。**
- Strategy 需要的是"当天及之前"的因子值
- ModelTrain 需要的是"历史全量"的因子值
- 同一个 `get_factor()` 接口同时服务两个场景，需要有明确的参数区分（是否需要未来数据）。

**问题3：Portfolio Manager 的位置不对。**
现在的数据流是 `Strategy → Portfolio → Backtest`，但 Portfolio 既在回测流程中（策略→组合→回测），又在执行流程中（组合→执行）。**Portfolio Manager 应该是独立于回测流程的模块**——它接收策略信号，输出融合后的信号，这个信号可以给回测引擎，也可以给执行层。

### 流程修正建议

```
DataHub → Feature → ModelTrain (离线训练, 输出ML因子到Feature)
                ↓
          Feature (含ML因子)
                ↓
          Strategy → Portfolio → Backtest (回测)
                              ↘ Execute (实盘)
```

## 12. 缺失模块评估

### 确实缺失的模块

| 模块 | 作用 | 必要程度 | 说明 |
|------|------|---------|------|
| **策略优化器** | 自动搜索最优参数组合 | 高 | 现在需要手动调参，效率低 |
| **数据版本管理器** | 确保回测可复现 | 高 | 没有这个，回测结果不可信 |
| **回测结果数据库** | 存储和对比所有回测结果 | 中 | 参数优化时需要 |
| **自动化报告生成器** | 每日自动生成标准报告 | 中 | 提升使用体验 |
| **紧急停止开关** | 一键停止所有交易 | 低 | 实盘时才需要 |

### 不是缺失，但定位不清晰的模块

| 模块 | 问题 | 建议 |
|------|------|------|
| **ModelTrain** | 和Backtest的时序关系没说清 | 明确为"离线预计算"模式 |
| **Portfolio** | 放在策略层不合适 | 提升为独立层，介于Strategy和Backtest/Execute之间 |
| **Cache** | 各层都有自己的缓存需求 | 统一到DataHub或独立缓存层 |

## 14. 最终结论

**框架的架构设计是专业的（7层、标准化接口、模块化），但在模块间协作的细节上有5个致命问题。** 如果这5个问题不解决，框架跑起来会出大问题（回测结果不可信、ML策略跑不动）。

**最核心的1个问题：模型训练和回测的时序关系。** 这直接决定了ML策略能否在框架中实现。如果这个问题不想清楚就动手搭，搭到一半会发现ML策略的回测实现不了，要回头改架构。

**框架整体成熟度评估（基于本次评估）：**
- 架构设计: 85/100 ✅
- 模块细节: 60/100 ⚠️ 需要修复5个致命问题
- 流程合理性: 55/100 ⚠️ 需要修正模型训练和回测的协作方式
- 模块完整性: 70/100 ⚠️ 缺少策略优化器和数据版本管理器

**在动手搭建前，必须先修复5个致命问题，修正模型训练和回测的协作方式。** 否则搭到一半会发现结构性问题，返工成本比现在改蓝图高得多。
