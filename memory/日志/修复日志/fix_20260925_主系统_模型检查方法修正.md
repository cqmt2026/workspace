## 问题回顾

在 17:27-18:17 的模型检查中，出现了多处误判：

### 误判 1: agnes-25 key 截断
- **错误**: models.json 显示 `sk-UF8…pN9e`（11字符），判定为"key 截断不可用"
- **真相**: Gateway 从加密 auth store 读取完整 key，models.json 只是脱敏显示
- **后果**: 错误标记 agnes-25 为 P0 待修，实际上它一直正常工作
- **修正**: 已承认错误，从报告中移除

### 误判 2: sensenova/deepseek-v4-flash 可用
- **错误**: 第一次测试 429 rate limit，第二次测试成功，判定为"临时 rate limit"
- **真相**: 可能说明 sensenova 的配额或 key 有问题，不应仅凭一次成功下结论
- **后果**: 高估了 sensenova 的可靠性
- **修正**: 标注为"需要持续监控"

### 误判 3: 忽略系统状态变化
- **错误**: 检查期间系统从 agnes-25 切换到 agnes-ai，但未及时关注
- **真相**: 系统切换本身说明 agnes-25 可能有问题（或用户手动切换）
- **后果**: 错过了重要的状态信号
- **修正**: 以后检查时要同时监控 session_status 的变化

### 误判 4: 检查方法缺陷
- **错误**: 用 Python 直接发 HTTP 请求，绕过 OpenClaw 认证机制
- **真相**: 看不到真实 key，无法正确测试
- **后果**: 结果不可靠
- **修正**: 应该用 OpenClaw 提供的工具链（`openclaw models auth list`、`session_status` 等）

## 正确的检查流程

1. **先看现状**: `session_status` 确认当前模型和工作状态
2. **再看认证**: `openclaw models auth list --json` 看所有 provider 的认证状态
3. **排查问题**: 对有 cooldown/error 的 provider，记录具体问题
4. **实测验证**: 只对真正怀疑有问题的 provider 做 HTTP 实测（用 OpenClaw 的 key，不是读文件）
5. **持续监控**: 检查不是一次性的，要关注系统切换行为
